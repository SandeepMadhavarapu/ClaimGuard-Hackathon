Measured results

Every number below was measured, and the misses are published on purpose. All documents are synthetic.

Held-out set B, real Gemini, on the deployed build (28b575a, Nov 28): of 32 readable documents never seen during development, ClaimGuard's private layout read extracted 19 correctly and held 8 for review. On 5, all O/0 or I/1 look-alikes, OCR misread one character on the correctly labeled line, so the value offered was off by one character; the confirmation step names those characters by position. Of 18 documents that must be held (conflicting references, pending, blank, denied or no payer reference), it held 18 and offered 0 as ready. On 5 of the conflict pages, Gemini picked a slot anyway, and the deterministic guard held every one. All 50 real requests (40.7 KB) were captured, and none contained a digit outside a slot name.

How the held-out sets were built

  • 50 distinct documents per set, generated from a fixed seed (evaluation/heldout/generate.py) across 6 layouts (letter, table, fax, memo, card, plain) and 5 fonts. Each set has 32 readable documents (familiar and unfamiliar label wordings, references in prose, the same reference printed twice, O/0 and I/1 look-alikes) and 18 that must be held (two different references on one page, two documents with different references, original and amended references, pending, blank, denied, not applicable, and hospital identifiers only).
  • Variants are reported separately. Ten documents per set also get a blurred, a low-resolution and a skewed, compressed copy: 30 variants, not 30 new documents.
  • Set A was generated and run against frozen code (e017a83) before any results existed. It exposed a real bug, so it became the development set. Set B was generated after the fixes with a new seed and four label wordings that never appeared during development, then scored once at e737968.
  • What runs here: the app's own modules in Chrome: on-device Tesseract OCR, the OCR label rule, the private-layout builder, the leak gate and the slot guard (evaluation/heldout/run.py). The model step needs Firebase App Check in a real browser, so this run reports it as a realistic model (it picks the one value whose own label says payer authorization) and as a best case. The real-model run is the Run held-out set B button in the app's benchmark panel. It paces itself under Gemini's free-tier limit of 15 requests per minute. A first attempt that didn't pace hit that limit after 19 documents, which is why pacing exists.

Set A: what the first held-out run exposed

Published misses

O versus 0, I versus 1. On held-out look-alikes, Tesseract read the correctly labeled value with one character wrong, at the same confidence (89–93) as correct reads, so confidence can't catch it. The guard holds the case when nothing confirms the value; otherwise the clerk's character check is the safeguard, and the app names each look-alike character's position. On the iPhone 12-scan run, Apple Intelligence and Vision OCR both read the trap's zero as a letter O.

Unseen label wording. In the real run, Gemini answered NONE for "Pre-approval no." and "Approval #:", two of set B's four new wordings, so those documents were held, not misread.

OCR misreads. On a few readable documents, OCR misread a digit of the value, and those were held.
